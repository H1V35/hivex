# Project foundation and adaptive workflow

HiveX distributes a small project documentation foundation, five independent workflow skills for design, documentation, implementation, review and Git/triage, plus the HiveX knowledge-support skill. The foundation extends [ADR 0010](0010-practical-knowledge-assistance.md); it does not turn the CLI into a development-session orchestrator or replace the principal reviewer.

## Initialize without taking ownership

`init` prepares only missing project Markdown, source configuration and Git visibility rules, without model calls. It preserves existing files and local knowledge. The responsible agent completes purpose, vision and domain language from project evidence and owner decisions, and may migrate useful material toward the recommended structure. Existing monorepo, package and module documentation authorities remain valid. Templates are optional starting points, not a required repository layout; retain useful content, links and history.

Project-local skill installation remains supported. `init` prepares a `CLAUDE.md` import of `AGENTS.md` and relative links for the six packaged skills in `.agents/skills` and `.claude/skills`, as later amended below. Existing skill entries remain project-owned, including custom or stale links; inspect them before changing them. Parent symlinks and incompatible path types fail validation before writes. The complete package supplies skill assets; moving its executable alone does not install them. Keep the presentation README short and use the packaged [CLI guide](../guide.md) for command details.

## Keep capabilities focused

Use the capabilities a task needs. Design, documentation, implementation, review and Git/triage skills remain independent; planning stages and extra tickets are not compulsory when the work is already defined. Triage labels describe readiness, participation, dependency, type, scope and risk for their distinct purposes. Labels neither select models nor grant permission. Preserve useful work labels such as `epic`, `research`, `prototype` and `decision` when skills change; avoid aliases that duplicate existing meaning.

Skills provide task knowledge and criteria. The host harness coordinates agents, applies model and effort configuration, and manages execution permissions, processes and session limits. Project Markdown owns workflow policy; HiveX's CLI owns source retrieval, versions, explicit coverage and authored navigation. Keep those responsibilities distinct instead of duplicating harness mechanics in skills. The CLI invokes no knowledge model.

## Engineering and independent review

Use mature engineering and documentation practices. Prefer domain-driven design and meaningful module responsibilities without imposing hexagonal architecture or speculative abstractions. Keep product, stack and host details in the adopting project. Work uses the checks that add value; no planning stage, extra ticket or testing ritual is required by itself.

Choose tests by value and risk, including critical flows, stable rules and regressions. TDD is optional and reserved for sufficiently defined critical behavior. Use one independent review by default; add another only when concrete risk or findings justify it. The reviewer uses a different model vendor than the implementation agent, as amended on 2026-10-03 below. The principal reviewer verifies conflicts with relevant decisions, dependencies and exceptions. CLI retrieval supports the responsible agent and is separate from independent implementation review.

Keep `AGENTS.md` a concise entrypoint with orientation, development and verification guidance, and indispensable project constraints. Links explain when an authority applies; they do not require every source on every task. Use the shared creation/update/archive date convention. Other metadata remains purpose-specific; the foundation imposes no proprietary knowledge schema or line-count limit. Skills use focused descriptions and conditional references, preserving the user's scope and existing authorization.

## Source-led integration

[ADR 0014](0014-reliable-markdown-and-explicit-relationships.md) governs knowledge before integration. Start from the documentation map and relevant Markdown authorities, then follow explicit dependency, exception and replacement links as the task requires. Review the affected sources together with the changed implementation. Resolve demonstrated contradictions, missing decisions needed for supported behavior, broken references and actionable defects. A model finding is a claim to check against the sources and code. Bound review to a defined source and implementation revision; close it when concrete findings are resolved; report a blocking owner decision explicitly, and handle new evidence as a bounded update rather than repeated whole-corpus certification.

The inferred graph runtime is retired, and its historical status is not an integration gate. Preserve graph snapshots and local work history, including failed results, quality marks, uncertainty and consumption. Do not reset accounting, erase evidence or relabel a historical/native result as success to clear a warning. A stale graph or unrelated warning alone does not block integration; a real current defect or unresolved decision affecting supported behavior does.

The former graph-completeness and zero-warning gate is retained in the [historical foundation decision](../archive/adr/0012-project-foundation-and-workflow.md#knowledge-before-merge-2026-09-18). ADR 0014 supersedes that gate while preserving project-specific owner decisions and existing merge authorization.

## Amendment (2026-10-03): cross-vendor review and runner pools

The owner replaced the same-model reviewer rule. A reviewer from a different model vendor surfaces defects a same-vendor review misses; in Compi it caught defects the same-model review had approved. Implementation currently runs on Claude Code, so the foundation's initial reviewer is `gpt-6.1-sol` with `xhigh` effort, read-only through Codex, following `hivex-review`. Projects record their reviewer profile in their engineering guideline and may change it while keeping a different vendor. The foundation ships the [independent review procedure](../../skills/hivex/assets/project/docs/procedures/independent-review.md) with its report schema.

The foundation also ships the [self-hosted runner pool procedure](../../skills/hivex/assets/project/docs/procedures/self-hosted-runners.md) for private projects running CI on their own machines: a pool of single-job runners, each with a private `HOME` so setup actions do not replace the owner's toolchain or each other's binaries. HiveX itself is public and keeps its GitHub-hosted runners under the [execution procedure](../procedures/self-hosted-runner.md).

`init` creates these files only when absent. Existing projects adopt them deliberately when updating HiveX.

## Amendment (2026-10-03): native `AGENTS.md`

`init` no longer prepares the `CLAUDE.md` import of `AGENTS.md` described above. Claude Code 2.1.277 and later reads `AGENTS.md` as project instructions when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists in the working directory or above it, so the import only duplicated the entrypoint and reappeared in projects that had removed it. Sessions where that support is [unavailable](https://code.claude.com/docs/en/memory#when-agents-md-support-is-unavailable), such as Amazon Bedrock or disabled telemetry before 2.1.281, still need a project-owned `CLAUDE.md` importing `AGENTS.md`. An existing project `CLAUDE.md` remains project-owned and is preserved.

## Amendment (2026-10-19): copied skills and pinned release

`init` no longer links the skills into the installed package. It copies the six skills, with their references, assets and language templates, from the executable into `.agents/skills/` and links each from `.claude/skills/`; Git ignores those per-machine links. The amendment of 2026-10-30 replaces the links with committed copies. A standalone executable therefore installs the skills. `hivex.json` pins the release, and `update` refreshes the copies and moves the pin forward. The [guide](../guide.md#initialize-a-project) describes the current behavior.

## Amendment (2026-10-19): reviewer when no other vendor is available

The cross-vendor reviewer remains the default and the reason above still holds. When no model from a different vendor is available, the review uses the implementer's vendor in a new session that never saw the implementation, and the review record states that independence level; it never falls back silently. The [independent review procedure](../../skills/hivex/assets/project/docs/procedures/independent-review.md) operates both cases, and the project's engineering guide records the profiles.

## Amendment (2026-10-23): the skills section of `AGENTS.md`

Agents skipped the HiveX skill a task needed, such as visual work done without `hivex-design`, even with the skills installed; a project had to write the routing rule into its own entrypoint by hand ([H1V35/compi#2075](https://github.com/H1V35/compi/pull/2075)). The bundled `AGENTS.md` now carries a marked section stating which skill each kind of work loads, with no exception for small changes, and that delegated work follows it. `init` writes it into a new entrypoint and appends it to an existing one; `update` keeps it current. That section is the only part of a project's `AGENTS.md` HiveX changes after creation, as the managed rules are of `.gitignore`; the rest of the file remains project-owned and the conciseness rule above still applies. The [guide](../guide.md#the-skills-section-of-agentsmd) describes the behavior ([#230](https://github.com/H1V35/hivex/issues/230)).

## Amendment (2026-10-30): committed skill copies for Claude Code

The ignored links of the amendment of 2026-10-19 existed only in the checkout that ran `init` or `update`. Claude Code loads project skills only from `.claude/skills`, and in a linked worktree it falls back to the main checkout's skills only when the worktree has no `.claude/skills` of its own, so every new clone and every worktree of a project that commits another Claude skill went without HiveX's skills (Compi, 2026-10-30). Committed links are no remedy: Git for Windows checks a symbolic link out as a text file unless the machine allows symlinks, and Claude Code offers no setting to read `.agents/skills`.

`init` and `update` therefore write the same managed copy of each skill into `.claude/skills/<name>/` as into `.agents/skills/<name>/`, and the project commits both. The release bundle stays the single source: `update` makes both copies identical to it and the inventory records both. `update` replaces Claude's former link to the copy in `.agents/skills` and removes the rules that ignored those links, so the copies reach Git; a link elsewhere stays project-owned. `init` keeps both, so it never exposes a link to Git. The [guide](../guide.md#initialize-a-project) describes the behavior ([#244](https://github.com/H1V35/hivex/issues/244)).

## Amendment (owner, 2026-11-26): recover before acting

In an adopting project, agents loaded the skills as the skills section requires but rarely ran `search`, `relations` or `read`. They briefed other agents from memory or from a context summary and took that context as verified, and reviews checked the diff without asking whether it ignored a documented decision, so the owner had to restate decisions already written. The skills allowed it: the `hivex` skill ran its commands «when they recover missing evidence» and reused «already verified current context» without defining it, and the context-reading method held that «another command is unnecessary if the needed context is already present». The owner decided: «Sí, hay que añadir lo que sea necesario para que se use HiveX en todo momento por cualquier agente antes de hacer nada, ya sea coordinar, implementar, revisar, hacer research, etc.», and authorized a release that closes the gap wherever HiveX is installed ([#258](https://github.com/H1V35/hivex/issues/258)).

Every agent, before any action on the project (coordinating, briefing another agent, implementing, reviewing, researching, documenting or answering a question about it), recovers with HiveX what has been decided on that topic and states the rules it applies with document, line and the owner's date. Verified context is only what the agent read from the current source version in its present context; remembered context, another agent's paraphrase and a context summary are not, so it recovers again after a compaction or summary. Every brief to another agent asks for that recovery and its list, every pull request lists the decisions it applies, and the independent reviewer recovers the decisions governing the changed area itself and reports any the change ignores or contradicts. The `hivex` skill states the rule; the workflow skills, the context-reading method and the review procedure template apply it; the skills section of `AGENTS.md` carries it into each project on `update`. That replaces the quoted wording. The rule asks for the decisions on the task's topic, not every source, so the conciseness rule above still holds.

Skills alone leave the rule to each agent's attention, so the owner added: «Creo que en HiveX debería de haber algo para que al instalarse se recomiende crear los hooks o similares para que se haga cumplir.» HiveX therefore ships the enforcement as an opt-in kit. `hivex hook` answers the lifecycle hooks of Claude Code and Codex: it reminds each session and subagent of the rule, records when it runs `search`, `read` or `relations`, and denies edits, agent and workflow launches, `git commit` and `gh pr create` until it has, and again after a compaction. It tells agents apart where the host's tool events identify them; Codex's identify only the session. It reads only documented hook fields, never the transcript, and lets through with a warning any input it does not recognise, so a change in a host's format cannot lock a session out. `init` and `update` also report, for each host whose settings directory the project has, whether its project settings register the kit, with the configuration and steps to register it when they do not. That extends [Initialize without taking ownership](#initialize-without-taking-ownership) by reading host settings only: HiveX never writes a project's host settings, so registering the kit stays the owner's decision in the host's configuration, and the harness still runs the hooks and owns permissions and processes as [Keep capabilities focused](#keep-capabilities-focused) says. The kit is a guardrail any retrieval command satisfies; reviews still check the rules a change states. The [guide](../guide.md#enforce-recovery-with-host-hooks) describes it.

The owner accepted three limits of the kit on 2026-11-26, as the guide documents them. In Codex, whose tool events identify only the session, a subagent shares its parent's recovery and the kit still denies until the session has recovered. A retrieval counts by the command line, not by which of its parts ran, so `cd <dir> && hivex search …` counts even when the `cd` fails. When a compaction cannot remove the record because its storage is read-only, the hook warns, and that record counts again once the storage is writable, until the session recovers again or ends.

## Amendment (owner, 2026-11-26): failures reach the agent, and review checks coverage

The kit lets a call through whenever it cannot apply the rule, so a change in a host's format cannot lock a session out. Its warning reached only the person, as `systemMessage`, and was kept nowhere, so a hook that let every call through after such a change would go unnoticed; and any retrieval command lifts the gate, whatever its topic. The owner decided: «Después, en HiveX: cuando el hook deje pasar por un fallo, que el aviso llegue también al agente (additionalContext) y quede registrado, para que un fallo silencioso se detecte. Y en cada PR, comprobad que «Decisiones que aplica» cubre el tema del cambio, porque una búsqueda cualquiera desbloquea el hook.» ([#261](https://github.com/H1V35/hivex/issues/261)).

When it lets a call through because it cannot apply the rule, the hook therefore adds the warning to the agent's context on every event whose host documents a channel for it, except where that channel changes what the event does, as in Claude Code's `Stop` and `SubagentStop`, where it continues the turn; it keeps `systemMessage`, and records the failure. The record follows [the lifecycle rule for runtime data](../guidelines/engineering.md#files-and-runtime-data-have-a-lifecycle). Its purpose is to show a failure that repeats. It belongs to the user, in the platform's per-user location for logs and state, not to a project: the hook answers events from any project, and some failing inputs name none. Each line holds only the time, host, event, a stable reason and a session hash, never the input's content. It keeps at most two files of 64 KiB, and a write that fails is skipped without changing the answer. `hivex hook --failures` reads it.

The hook cannot tell whether a recovery covered the change's topic, so review checks that. The reviewer checks that the pull request's list of decisions covers every area the diff touches and reports an uncovered area as a finding, and the review's verification names the HiveX commands it ran in the session that reviewed the final revision; a report without them is incomplete. A pull request is not ready while its list leaves an area uncovered. `hivex-review`, `hivex-git` and the independent review procedure template apply this, and the [guide](../guide.md#when-the-hook-cannot-apply-the-rule) describes the hook's part.

## Amendment (owner, 2026-11-26): a proportionate failure record

The record 0.16.0 shipped took turns through a lock, refused links and named pipes, ended lines an interrupted write had left unfinished and left alone a current file past its limit, with the `libc` dependency and a test for each. The owner judged it out of proportion: «Sobre HiveX 0.16.0: funciona, pero el registro de fallos no es proporcionado a lo pedido. Abre una issue en HiveX para simplificarlo: que solo añada la línea y empiece un archivo nuevo al llegar al límite, sin bloqueos ni defensas contra carreras o enlaces y sin la dependencia libc. Quita también las pruebas que solo protegen esa maquinaria y reduce la sección de la guía a lo que necesita quien lo usa. Mantén lo que pedí: el aviso al agente, el registro sin contenido con tamaño máximo, --failures y la comprobación de cobertura en las revisiones.» ([#263](https://github.com/H1V35/hivex/issues/263)).

A failure therefore only appends its line; when the line would take the current file past 64 KiB, that file replaces the previous one and a new one starts. `hivex hook --failures` reads both files and counts the lines it understands. The warning to the agent, the content-free record capped at two files of about 64 KiB, `--failures` and review's coverage check stand as the amendment above decided; with no lock, failures at the same moment can pass that size by a line or rotate twice, as the owner's request accepts. The removed machinery remains only in the `v0.16.0` release. The independent review procedure template also covers the two cases a review's coverage check missed: a review that ran before its pull request was opened, and a list of decisions that changed without a new commit. The reviewer's session is resumed with the current list and checks it against the full diff it reviewed, and the earlier reports are kept.

## Amendment (owner, 2026-11-27): read-only helpers recover, the deciding agent rereads

An agent that recovers a lot fills its context with passages, and each summary then makes it recover again. The [recover-before-acting amendment](#amendment-owner-2026-11-26-recover-before-acting) holds that another agent's paraphrase is not verified and gives no place to helpers that only search. In an adopting project the owner approved having read-only subagents do that recovery, for every agent and, if possible, for Codex reviews, and approved updating HiveX for it, as the project's record of the decision ([H1V35/compi#2384](https://github.com/H1V35/compi/issues/2384#issuecomment-7228727193)) and the summary in [#269](https://github.com/H1V35/hivex/issues/269) report.

An agent may therefore leave the searching to read-only helpers, which change nothing. A helper searches and follows relations with HiveX and returns the passages verbatim with their document, lines and version, including the exceptions and replacements beside them, never a summary. That quote is enough to orient the agent and for what it does not apply as a rule. Each rule the agent applies, cites in a brief or in a pull request's list of decisions, or shows the owner in a conflict, it reads itself with `read` on the exact range, so verification stays with the agent that decides and the definition of verified context above stands. This holds for every agent and, where its harness allows helpers, for the independent reviewer, whose verification still names the HiveX commands it ran. The recovery hook does not change: it still denies agent launches until the session has run a retrieval, so an agent it gates starts with a focused search of its own before launching a helper. A helper's brief asks for those passages instead of a list of applied rules. The `hivex` skill states this; `hivex-review`, the context-reading method and the review procedure template apply it; the skills section of `AGENTS.md` carries it on `update`. Launching and bounding helpers stays with the harness, as [Keep capabilities focused](#keep-capabilities-focused) says.

## Relationships

- Extends [Product contract](0010-practical-knowledge-assistance.md): adds the project foundation and independent capabilities without making every phase mandatory.
- Depends on [Reliable Markdown](0014-reliable-markdown-and-explicit-relationships.md): source-led integration preserves explicit authorities, revisions and applicable defects.
